# PRD · ITSDEV Engineering Fieldnotes

> v4 · 2026-10-07 · 상태: 구현 전 명세 / 제안 디자인 방향 확정안
> 구축 범위는 itsdev.kr 포털이다. 기재된 서브도메인은 사용자 확인에 따라 이미 운영 중인 외부 서비스로 취급한다. 서버 구성·측정값을 검증한 결과는 아니다.

## 1. 제품 정의

ITSDEV는 직접 서비스를 만들고 운영하며 얻은 판단을 기록하는 기술 출판 공간이다. 독자는 문제 해결 기록을 읽고, 설계 근거를 확인하고, 관련 서비스를 탐색한다. 루트 도메인은 독립적인 콘텐츠를 제공한다. DJC로 전체 리다이렉트하지 않는다.

브랜드 문장: **“만들고, 운영하고, 근거를 남깁니다.”**

목표 우선순위는 ① 재방문할 만한 기술 콘텐츠 ② Public 서비스 발견 ③ 독서 경험을 유지하는 광고 수익화이다. 승인과 수익은 보장하지 않는다. 소유자 성하(aerofleet), 1인 개발·운영, 기존 OCI/Cloudflare/GitHub Actions를 활용한다.

## 2. 독자와 핵심 여정

| 독자 | 들어오는 계기 | 제공 가치 | 완료 행동 |
|---|---|---|---|
| 백엔드·인프라 개발자 | 검색으로 장애 해결 글 유입 | 환경·판단·설정·검증·한계 | 관련 기록으로 이동 또는 RSS 구독 |
| 개발 직군 구직자 | 공고/직무 정보 탐색 | DJC 소개와 직접 운영한 개발 기록 | DJC 공개 화면 이동 |
| AI 제품/HR 담당자 | 온보딩 시스템 사례 탐색 | WithBuddy 사례·적용 조건 | 서비스 소개 읽기 또는 문의 |
| 운영자 | 포털 콘텐츠 발행·배포 | Git 기반 편집·정적 배포 | 검수 후 포털 release 배포 |

주 여정: 검색 → 아티클 → 관련 아티클 → 서비스 사례 → 서비스. 홈의 대표 기록은 인기순 자동 집계 대신 편집자가 선정한다. 숫자가 없는 단계에는 가짜 조회수·상태·성과를 표시하지 않는다.

## 3. 구축 범위와 기존 서비스 참조

구축 대상은 itsdev.kr 하나이다. 기재된 서브도메인은 모두 이미 서비스 중이라는 사용자 확인을 반영한다. 이 프로젝트에서 신규 구축·재배치·인증 재설계·기능 변경을 수행하지 않는다.

포털은 Public 서비스의 소개 글과 외부 이동 링크만 제공한다. 기존 API나 Internal 도구는 포털 메뉴·sitemap·RSS에서 제외한다. 운영 중이라는 사실과 누구나 이용 가능한 Public 서비스라는 조건은 구분한다.

| 기존 서비스 | 포털에서 다루는 방식 |
|---|---|
| DJC 사용자 서비스 | 개발 사례·서비스 소개·공개 이동 링크 |
| myai 사용자 서비스 | 실제 서비스 설명·이용 조건에 맞춘 소개 링크 |
| WithBuddy | 개발/운영 사례 콘텐츠 |
| API·관리·개인 에이전트·관측 도구 | 공개 탐색 링크 제외, 기존 운영 변경 없음 |

서비스 소개를 위해 로그인 통합·API 호출·통합 proxy를 만들지 않는다. 제품 설명과 링크의 정확성은 포털 콘텐츠 검수 항목이며 서비스의 출시·배포 과제가 아니다.

| ID | 기능 | 수용 조건 |

경로: `/`, `/articles/`, `/articles/category/{category}/`, `/articles/{slug}/`, `/services/`, `/services/djc/`, `/services/withbuddy/`, `/about/`, `/contact/`, `/privacy/`, `/terms/`, `/rss.xml`, `/sitemap.xml`, `/ads.txt`.

검색·회원·댓글·추천 알고리즘·실시간 공개 상태 대시보드는 MVP에서 제외한다. 목록 필터는 서버 없이 정적 링크로 동작한다. 기존 서비스 제품 관계는 소개 글에서 정확히 설명할 정보이며 신규 설계 과제가 아니다.

## 5. 콘텐츠와 수익화

초기 목표 15편은 내부 편집 목표이다. 편당 1,500자는 초안 점검 참고값이며 Google 승인 요건으로 표현하지 않는다. 짧아도 독자의 문제를 완결하면 게시할 수 있고, 길어도 근거가 없으면 보류한다. 초기 공개는 완성된 대표 글 5편으로 가능하되 심사 신청 전 전체 콘텐츠 품질을 재검토한다.

기존 서비스의 운영 경험은 아티클 소재로 사용할 수 있다. 소스·수집·DB·API 등 실제 구현에 관한 설명은 저자가 확인한 사실만 기록하며, 포털 구축을 위해 해당 서비스를 변경하지 않는다.

Tistory와 동일 내용을 배포할 때는 대표 원본 한 곳을 선택한다. 외부 canonical은 검색 대표 URL에 영향을 주는 신호이며 콘텐츠 독창성이나 광고 심사 통과를 대신하지 않는다. ITSDEV에는 운영 후속 검증·환경 차이·새로운 해설을 더한 독립 글을 우선한다.

AdSense는 루트 도메인을 등록하고 소유권 확인·크롤러 접근·계정의 Ready 상태를 확인한다. 광고 구현과 검수 범위는 itsdev.kr이며, 기존 서비스의 광고 적용은 별도 운영 과제이다. 승인 전 자동 광고를 켜지 않으며, 초기에는 아티클 후반과 종료 구간 최대 2슬롯을 검토한다. 실제 publisher ID만 사용한다.

## 6. 품질 목표와 측정

| 항목 | 목표 | 측정/판정 |
|---|---|---|
| LCP | 모바일 목표 ≤2.0s, 출시 게이트 ≤2.5s | 대표 3페이지 동일 모바일 lab 조건 3회 중앙값, 환경 기록 |
| CLS / INP | ≤0.1 / ≤200ms | lab + 트래픽 확보 후 field p75; field 자료 없으면 미측정 |
| TTFB | warm edge 목표 ≤200ms | 측정 지역·HIT 여부 기록, cold 응답 별도 |
| 자체 JS | 공통 UI 압축 합계 ≤8KB | 광고/CMP 별도 계측, 핵심 읽기는 JS 불필요 |
| 가용성 | 월간 99.5% 내부 목표 | 외부 probe로 HTML+본문 확인, 캐시 장애 대응 보장 금지 |
| 리소스 | 평시 MemAvailable ≥20%, swap-in/out 지속 없음 | 노드별 실제 부하 관측; swap 점유만으로 장애 판정 금지 |
| 보안 | 포털 origin 직접 접근 차단 | 포털 loopback·외부 거부, 기존 공유 인프라 설정 유지 |

초기 30일은 baseline 수집 기간이다. 검색 유입, 관련 글 이동률, 서비스 이동률을 관측하되 수익 예측과 트래픽 수치는 데이터 확보 전 제시하지 않는다. 분석 도입 시 개인정보·쿠키 고지를 함께 검토한다.
